# Hints — when the answer does not come

A blank or near-blank answer is never sent back empty-handed. It is not a failure; it is a signal to give more.

## 1. Default: the polished answer is already a hint

In the default loop (core.md §4) the user talks first and the tutor polishes. When the user cannot start at all,
give the frame for the question's type (grading.md §3) as **keywords, one line per slot** (`slot: what > what`).
Do not stack blanks, a fill-in sentence and a material table at once; one layer is enough.

## 2. The ladder (users who chose "let me try first", and blank answers)

| Step | The tutor gives |
|---|---|
| 1 | Which experience card or ledger row holds the material (named and quoted, not just an id) |
| 2 | Which part of it answers this question |
| 3 | The first sentence of that part, read out |
| 4 | Write together: the tutor gives a three-line skeleton, the user fills it in their own words |

After step 4 an answer always comes. That spot goes under "Stuck" with a card.

- Climb one step per turn. Do not jump to the polished answer for a "try first" user unless they ask.
- **The question stays the same while climbing** (grading.md §4). Hints sit outside the question.
- If the user does not understand a concept inside the question, stop climbing: modes/research.md first.
  Rehearsing an answer about something unknown only glues submitted sentences together.

## 3. The v0 rule

Every polished answer the tutor writes is a **v0**: someone else's arrangement of the user's material.

1. **Say it is v0** the first time in a session: "This is my arrangement of what you said. Memorised as is, it falls
   over in two follow-ups. Read it aloud and tell me what sounds wrong."
2. **The user reads it aloud and picks what sounds off.** That is where v1 starts. The sentences that come out of the
   user's mouth replace the tutor's.
3. **Material is limited to** what the user said in this session or earlier sessions, the facts ledger and the
   submitted documents. The tutor adds only order and connectives.
4. Store versions: the experience card keeps slot keywords per version; the practice log keeps v0 and what the user
   changed. Never delete an older version.
5. Mark where the user's own wording survives (e.g. `<!-- user's words -->` in writing drafts), so a later session
   does not smooth it again.

## 4. When the user asks "just write it"

Give the full example at the top (core.md §8), built per §3. Then the one line about what changed, then the question.
Asking for an example is never a failure and never needs justifying.
